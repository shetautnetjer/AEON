# AEON operating rules

AEON owns navigation, organization and its existing observability pilot files. Linked projects keep their own Git/source/contract owners. Read [PROJECT.md](PROJECT.md), [STATUS.md](STATUS.md), [DECISIONS.md](DECISIONS.md), then the relevant owner before acting. Current creator/session instructions and authorized scope govern; these documents grant no new permissions or identity.

- Use local source and dated receipts for project truth. Distinguish installed, configured/deployed, historically tested and qualified. A diagram, saved note or test count is not useful memory or production acceptance.
- Reuse existing HLD/Guide/Dictionary/schema owners through [Bible navigation](bibles/README.md). `bibles/` is the physical Bible path; preserve it. Authored JSON/Markdown govern navigation; HTML/SVG are derived views. Its dated index is not a fresh runtime inventory.
- Preserve `.git`, `.trigger-tree/`, unrelated dirty work, historical failure/zero-gain evidence and original receipt paths. `worktrees/` remains excluded from AEON Git. Commit only owned source/test/docs files in the correct repository; no blanket staging, remote push or duplicate project homes.
- Keep credentials, private session bodies, databases, raw native logs and binary/runtime state out of navigation Git. Do not read/write private Cloud/Notion/Basic Memory Cloud under the current local-only task scope. No memory/SOUL/profile mutation follows from organization.
- Continue authorized reversible source/test/docs work. Bring exact proposals for new live integrations, installations, service/cron/daemon changes, outbound/private telemetry, provider changes, data admission or physical relocation when they lack current authorization. Preserve model/run budgets and fail closed at required gates.
- [Work index](work/README.md) links task owners; do not copy their HLDs, code, contracts or receipts into queue folders. One owner per task, stable task ID, separate worktrees where concurrent edits collide. Reviewer and producer roles remain distinct where the local contract requires independence.
- Event-based coordination is the selected direction: task-ready, blocked, review-ready, completed. Future handling must be idempotent and preserve task/attempt/event identity. Existing platform completion notifications operate in the current coordination session; local `.trigger-tree/` metadata is not proof of an operating dispatcher. Evaluate its source before introducing another runtime.
- Update the existing task/status/decision owner with evidence and next action. A blocked or inconclusive attempt stays recorded. A bounded work loop chooses one owned item, implements/tests/reviews/commits, checkpoints and stops at its gate; this rule does not authorize an autonomous daemon or budget.
- Add nested AGENTS only when an independently scoped area's complexity needs distinct rules. Avoid boilerplate duplication.

- For a task handoff, keep one named owner and a dated task progress file under `work/`; list completed and unfinished checks with exact evidence references. `resources/` routes existing input/evidence owners, `outputs/` routes authored reviews/results, root `STATUS.md` points to the actual current task state, and `inbox/` stays untriaged until assigned. Distinguish inherited evidence, independently reverified work and new conclusions. A custodian may add navigation but cannot sign reviewer acceptance. Preserve frozen materials/criteria; a handoff grants no extra model budget. Current flow uses manual/platform events, with no new daemon.

- Keep changes small and scoped to the selected owner/task; use the existing plan and done criteria to stop scope drift. When approval is required, approve meaningful scope, effects and budget once; routine implementation, fixes, verification and already-approved integration steps continue within it. Ask again only for an actual change in authority, effects, scope or budget, or a specific unmet gate.
- After two failures of the same approach, preserve both receipts and change to bounded diagnosis or a different source-grounded strategy. This grants no extra model calls/retries and never overrides an explicit stop gate. Record concise sanitized lessons with the existing owner, exact source/receipt references and applicability limits.
- Report evidence by class: local/fake or unit checks, actual integration checks, deployed configuration, and production qualification. Passing one class does not silently qualify another; retain failed and not-run denominators.
